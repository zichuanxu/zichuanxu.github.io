title: "What 183 timers taught Lauren Tan about coding agents"
description: "A flicker in a desktop app, a convincing screenshot, and a release with 50 findings illustrate how Tan decides when to trust an agent's patch."
---

On September 9, a coding agent fixed a flicker in Cursor. VS Code and React were trying to update the interface at different times. The agent deferred one operation with a timer and left a comment explaining why. By October 3, the same technique had found its way into a shared module. On October 17, Lauren Tan showed a count of 183 timers. Creating and discarding them was giving the garbage collector work to do. [Tan walks through the timer history](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=442s).

I keep coming back to that first patch. A reviewer could have watched the flicker disappear, read the explanation, and approved it in good faith. The next agent would then find a working example with a persuasive comment and the team's apparent endorsement. What would I want that agent to find in the repository instead?

## Put the reviewer's decision where the agent will encounter it

Tan's later work on Grok Bot offers one answer. In an Electron app, the renderer handles typing and drawing. An innocent-looking import can pull expensive main-process code into the renderer and make keystrokes lag. The team's Dune framework gives each process its own directory. A dependency check rejects direct imports across that boundary, and a third directory holds the types that both processes need. An agent writing its first feature gets the same feedback an experienced reviewer would give, while the offending import is still in front of it. [Tan on Electron process boundaries](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=369s).

The team took a similar approach to React's `useEffect`. A small set of framework APIs owns the effects, including decisions about when they rerun and when to clean up. Feature authors call those APIs. I like Tan's test for whether a new rule earns its place: take an actual mistake from the repository's history and run the check against it. For a repository full of old examples, the team can start by catching new violations while it cleans up the ones an agent might copy. [Tan on framework APIs](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=303s) · [The pstack guide to correcting recurring mistakes](https://github.com/cursor/plugins/blob/0b46ec399d55f2829e88822998f53b84944837d3/pstack/skills/correct/SKILL.md).

## Give the agent a way to see the bug

At Cursor, Tan found herself collecting performance profiles for an agent that could already offer plausible explanations for a slowdown. She gave it tools to launch the app, simulate input, and collect CPU profiles and heap snapshots. Now it could repeat the same interaction before and after a change. If typing felt faster, the reviewer could inspect which work had disappeared from the profile. [Tan's account, *Loops You Can Trust*](https://x.com/poteto/status/2069824386283319343).

A feature map makes that approach useful for ordinary bug reports, too. Someone can point to “that thing in the sidebar” without knowing the component name. The map describes where to enter a feature, what actions to take, and what the user should see. Consider a conversation switcher that occasionally highlights the wrong row. I'd give the agent two conversations, A and B, and ask it to switch from A to B and back. On returning to A, the title, selected row, and messages should all agree. A recording of the failing sequence and another after the patch let a reviewer check all three, including a selection that briefly jumps to the wrong row. [Tan demonstrates the feature map](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=601s).

The choice of evidence matters. When Cursor migrated shared UI components from SCSS to StyleX, the sampled states matched pixel for pixel. People using the app still found elements stacking in the wrong order and components that depended on an old global class name. The team narrowed each migration to one leaf component, searched for consumers of its old classes, and checked themes and interaction states such as focus and hover. A screenshot could answer whether one button looked right. Finding out who else relied on its class name required a different check. [Tan's migration retrospective](https://x.com/poteto/status/2069824386283319343).

## Decide what the evidence is enough to ship

At Cursor, a feedback report could lead to a draft pull request. The agent checked the version and duplicate reports, reproduced the failure twice in a running build, and saved the evidence. A person could correct the diagnosis before a fix began. At Grok Bot, cutting a release started a cloud run in which agents exercised the new build and could open and merge fixes. One Linux run produced 50 distinct findings. Running the same checks against the previous version showed that 47 already existed. That comparison gave the release engineer three new regressions to investigate first. [Cursor's feedback workflow](https://x.com/poteto/status/2069824386283319343) · [Grok Bot's release check](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=976s).

Tan's public pstack workflow adds a detail I'd borrow for any automatic merge. One agent owns the pull request and an independent verifier examines the revision about to land. If a subsequent edit or rebase changes the patch, the verifier checks the new revision. Otherwise, a green result can quietly become evidence about code that nobody is shipping. [The pstack verification and shipping guide](https://github.com/cursor/plugins/blob/0b46ec399d55f2829e88822998f53b84944837d3/pstack/docs/guide/06-verify-and-ship.md).

## What I'd measure

In October 2026, Tan reported shipping 3,127 pull requests personally. The Grok Bot team merged 10,926. The often-quoted 0.47% revert figure belongs to the team. Tan described reverted PRs aloud, while the slide labels the measure as reverted commits. A bug fixed in a follow-up patch can escape either count. The team's client measurements tell a more tangible story. From May to the talk, cold startup fell from 2,304 to 1,395 milliseconds, and median typing time in a long conversation fell from 8.4 to 2.9 milliseconds. Idle memory rose from 488 to 545 MiB over the same period. [Tan's personal count](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=47s) · [Team delivery and client measurements](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=817s).

For my own work, I'd start with one recurring bug and follow a single repair all the way through review. Where did the agent have to wait for someone to operate the app? Which design decision did the reviewer have to explain again? On the next bug of that kind, I'd want to know whether a tool let the agent reproduce it unaided, whether a check caught the old mistake, and whether I could replay the evidence myself. Those are things I can learn from two repairs, long before I have thousands of PRs to count.
